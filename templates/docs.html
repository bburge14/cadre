Sessions

A session is one running Claude Code (or Gemini/Codex/Kimi) conversation, rooted at a working directory on this machine. "+ New session" on the dashboard lets you pick a label, a provider, and either a local directory or a GitHub/GitLab repo to clone (if you've connected one — see below).

Each session's page has Start/Stop/Restart/Delete, plus an interactive terminal ("Open terminal") — a real xterm.js terminal into that session's process, not just a read-only log. For Claude sessions this is in addition to connecting via claude.ai/code (Remote Control); for Gemini/Codex/Kimi it's the only way to interact with them from here, since none of them has an official remote-control equivalent yet.

If a session hits a usage/rate limit, its row gets an orange "limit hit" tag and its detail page shows the actual message — it clears itself the next time you restart that session.

"Hand off to fresh session" (on a session's own page) retires a long conversation by creating a brand-new session in the same directory and stopping the old one — it also writes a short note into that directory's CLAUDE.md telling the fresh session to check for a PROJECT_STATUS.md-style file first, so it doesn't have to re-derive context another session already captured.

Terminal & themes

Beyond the inline terminal on a session's own page, /terminal (the "Terminal" link in the nav) is a dedicated hub: a session sidebar grouped by whichever Agent Stack controls each session's directory, with whichever one you pick shown full-size next to it. Each session also has its own bookmarkable, chrome-free page at /sessions/<id>/terminal — handy for adding to a phone's home screen.

Resizing the browser resizes the real pty, not just what's drawn on screen — a full-screen program like Claude Code itself actually gets told its terminal changed size and uses the extra room, the same way a native terminal window would.

The theme dropdown right on the terminal page (not in Settings — it's about the CLI inside a session, not the dashboard) has 17 color options: Dark/Light/Auto plus named palettes (Dracula, Solarized, Nord, Monokai, Gruvbox, Tokyo Night, One Dark, Catppuccin Mocha, Synthwave, Matrix, Ayu Dark, GitHub Dark, Cyberpunk). Changing it applies to every session immediately, including ones already running — though a session that's already open needs its own Start/Stop/Restart to actually pick up the new config, the same way any program needs to reload its config to notice a change.

Agent stacks

A stack is one directory's own agent team — a set of Claude Code subagents that only apply to sessions rooted in that directory (or a subdirectory of it). This is Claude Code's own native per-project .claude/agents/ override, not anything Cadre invents; a stack pointed at ~/projects/myapp just means "write agent definitions into ~/projects/myapp/.claude/agents/."

Creating a stack

"+ New stack" on the dashboard — give it a name and a directory (the field auto-fills from the name as you type, edit it freely; the directory is created automatically if it doesn't exist). Then either click a preset (Generalist, Coding, Content/Writing, Research/Analysis, DevOps/Infrastructure, Data Science/Analytics) or check individual agents from the library. You can leave both empty and add agents one at a time afterward instead. Not sure which preset fits? Generalist — a bit of code, writing, research, and analysis, nothing deeply specialized — is a reasonable default to start from.

The directory doesn't have to be new or empty — pointing a stack at an existing project or an already-cloned repo is completely fine, it only adds/updates the .claude/agents/ folder inside, nothing else in that directory is touched. The directory field autocompletes from directories Cadre already knows about (existing sessions' and stacks' workdirs); a session's own detail page also has a "Create a stack for this directory" shortcut so you don't have to type/copy a path at all.

Editing a stack's agents

"Edit" on a stack opens its page: a table of that stack's agents with Edit/Delete, plus "+ New agent" to write one from scratch directly in that stack. Editing an agent lets you set its name, description (what Claude matches a request against to auto-delegate to it), tools, which other agents it can itself spawn, which skills it should use (see "Skills" below), model, and system prompt.

Diagrams

"Diagram" on a stack shows its hierarchy — every agent in that stack, with lines from "Coordinator" (the top-level session) to each one, and lines between agents showing who can delegate to whom. Click an agent to change what it's allowed to spawn. An empty stack's diagram says so plainly instead of looking the same as a populated one.

project-scribe: continuity across sessions

Every preset includes project-scribe — it keeps a single PROJECT_STATUS.md at the project root current (what the project is, current state, recent changes, open threads, anything non-obvious worth knowing), so a fresh session — a different stack, a different day, a different provider entirely — can read it and actually continue the work instead of starting cold. The other agents in each preset are wired to delegate to it after meaningful work, so it happens without you having to ask each time. Add it to a custom stack from the library if you're not using a preset.

"Global (default)" — not a separate system

There's no separate "global" page. ~/.claude/agents/ and ~/.claude/skills/ — the one team Claude Code always falls back to for a session not covered by a more specific stack — shows up as an ordinary row, "Global (default)," at the top of the same Agent Stacks list. Same Diagram/agents-table/skills-table page as any other stack; it just can't be renamed, moved, or deleted, since there's no directory to point elsewhere and nothing meaningful to delete. Want a whole preset applied there? Open it and use the same preset picker any stack has. It's also seeded with the Generalist preset automatically the first time it's ever found empty (once — clearing it out on purpose later won't bring that back), so a fresh install isn't just staring at an empty default team.

Skills

A skill is a different mechanism from an agent: it's a packaged, reusable set of instructions that gets loaded into whatever session invokes it (the top-level coordinator, or a subagent) — not a separate spawned worker with its own context window the way an agent is. Think of it as handing the current session a specific playbook, rather than delegating the work to someone else.

Unlike agents, skill definitions aren't scoped per stack — there's one shared list ("Skills" in the dashboard nav, ~/.claude/skills/), usable by every agent in every stack. Create/edit/delete works the same as agents but simpler: a skill only needs a name, a description (what it does and when to use it), and the instructions themselves — no tools/model/spawn-graph, since a skill runs in the invoking session's own context rather than as a separate agent.

That one list comes seeded with three example skills — one per major flavor the Generalist preset spans, so there's a concrete answer to "what's a skill actually for" instead of an empty list: commit-message-style (a reference for how commits should read), writing-tone-guide (style guidance for anything written for someone else to read), and research-source-checklist (what to check before trusting a source). Genuinely usable as-is, but really meant as a template — edit or delete them freely.

Attaching a skill to a specific agent happens on that agent's edit page — a searchable "skills" checklist there, pulling from the same shared list. Checking a skill there doesn't rely on Claude Code natively supporting a per-agent skill field (nothing confirms that exists) — it rewrites the agent's own system prompt with a short auto-generated section naming the selected skills and their descriptions, telling the agent to invoke them by name when relevant. Reliable regardless of the exact native mechanism, since it's just plain instructions in a system prompt.

This is newer and less battle-tested than agent management — the file format (<name>/SKILL.md with name/description frontmatter) is confirmed correct against real skill files already on this machine, but hasn't yet been verified end-to-end against Claude Code actually loading a Cadre-created skill in a live session.

AI providers

Every agent in every stack is still a Claude Code subagent — that's not optional, and it's why Settings has no "Claude" API-key field. What you're logged into is the claude CLI itself. Settings shows your actual state instead of a login form:

  • claude not found — you have an Anthropic account but not the CLI installed; that's a one-time terminal step Cadre can't do for you (npm install -g @anthropic-ai/claude-code).
  • Installed but not logged in — create a session, open its terminal, run /login there.
  • Installed and logged in — nothing to do.

Gemini, Codex, and Kimi are optional and API-key only — paste a key for whichever you use in Settings. Settings also flags whether each CLI is even found on your PATH.

Setup wizard and "Default AI"

The setup wizard (shown once right after creating your admin account, or reachable anytime from Settings) walks through picking a provider, connecting it, and setting it as your default AI — this pre-fills the provider on "+ New session" and is the one used to run your Agent Stacks. The default picker only ever offers providers that are both actually connected and capable of running a stack at all. Claude is the only one confirmed end-to-end; Gemini, Codex, and Kimi have each since shipped their own native subagent mechanism and Cadre now translates your agents into each one's format automatically, but none of the three has been run against a real install by anyone yet — expect rough edges if you're the first to actually try one (see "Agent Stacks on other providers" below).

Agent Stacks on other providers

Every time you save, delete, or activate an agent (individually or via a preset), Cadre also writes that same agent out in the native subagent format of the other three CLIs — the exact same definitions you manage here, translated automatically, no extra step. This happens alongside .claude/agents/, which stays the one source of truth; the other three are always regenerated to match it, and only the file matching that specific agent's name is ever touched, never the rest of that directory.

ProviderWhereFormat
Codex.codex/agents/<name>.tomlTOML
Gemini.gemini/agents/<name>.mdMarkdown + YAML frontmatter
Kimi.kimi-code/agents/<name>.mdMarkdown + YAML frontmatter

What doesn't translate, deliberately: model/effort (cross-vendor model names aren't equivalent by string, so each CLI just uses its own default) and skills (each CLI's own skills mechanism, if it has one, uses a different file format — skill descriptions are folded into the agent's instructions text instead, the same plain-instructions approach Claude's own skill attachment already uses). Gemini specifically can't delegate to other subagents at all — a hard limit of Gemini CLI itself, not a gap in this translation — so which agents a Gemini agent "can spawn" has nothing to map to there. Gemini's tool restrictions also aren't translated (its tool identifiers aren't a confirmed match for Claude's), so a Gemini agent always inherits every tool regardless of what it's restricted to here.

Schemas confirmed against each CLI's own documentation. None of the three has been run against a real install by this app's own author — Claude is the only provider confirmed end-to-end. If you test one and something's wrong with the generated file, that's expected territory right now, not a settled feature.

Delegating an agent's work to another provider

Editing an agent lets you pick a "primary AI for this agent's actual work." Choosing Gemini/Codex/Kimi there rewrites that agent's instructions with an auto-generated block telling it to shell out to that provider's non-interactive mode and treat the result as its real answer. The agent itself is still a Claude Code subagent doing the orchestrating — this doesn't reduce Claude usage, it's for when you specifically want a different model's output on a given agent's tasks.

Connecting GitHub / GitLab

Optional — only needed if you want "+ New session" to clone a repo instead of pointing at a directory already on this machine. In Settings, register an OAuth App (GitHub: github.com/settings/developers; GitLab: your instance's User Settings → Applications) using the exact callback URL Settings shows you, paste the Client ID/Secret in, save. "+ New session" then shows a "Connect your account" link on the GitHub/GitLab tab.

Dashboard appearance

Separate from the terminal theme above — Settings > Appearance picks this dashboard's own look, not the CLI inside a session. 3 static themes (Default, Circuit Board, Slate) and 4 animated ones (Galaxy, Aurora, Code Rain, Ember), each with its own accent color too, so buttons/links/badges shift along with the background instead of staying the same blue regardless of theme. Picking one saves immediately, no separate "Save" click needed.

Account & recovery

This app has exactly one admin account, created during the one-time /setup wizard. Since there's no email tied to it to send a reset link through, a security question (required at setup) is the recovery path instead — "Forgot your password?" on the login page asks the question, and a correct answer lets you set a new password. Both login and recovery attempts are rate-limited with the same backoff, so repeated wrong guesses just get slower, not locked out forever.

Settings > Account changes username, password, or the security question/answer — any change there requires your current password first, same as any real account settings page. If you forget the security answer too, a terminal-based script (reset-admin.sh / .ps1 / .bat, in the repo) is the hard fallback — see "Locked out?" in SETUP.md.

Reaching it from other devices

By default this only listens on the machine it's running on. Step 4 of the setup wizard and Settings > Network both show whether that's still the case, and if Tailscale is installed and running on this machine, show its IP directly — no digging through .env or a terminal to find it.

Getting reachable from another device always takes the same two steps first: set CADRE_HOST=0.0.0.0 in .env, then restart it. That alone is enough on a trusted home LAN — anything else on the same network can then reach http://<this-machine's-LAN-IP>:7420.

Tailscale (recommended) puts this machine and your other devices on their own private network reachable from anywhere with an internet connection — no port-forwarding, no public exposure, no dynamic DNS. Install it on this machine and whatever device you want to reach the dashboard from (tailscale.com/download), sign in on both with the same account, then find this machine's Tailscale IP with tailscale ip -4 (or check the wizard/ Settings > Network pages above, which show it automatically). Open http://<tailscale-ip>:7420 from the other device — works over cellular data too, not just shared Wi-Fi.

Plain LAN needs no install beyond the two steps above — just use this machine's regular LAN IP instead of a Tailscale one. Only reachable from devices on the same local network, and only while this machine's IP doesn't change.

Port forwarding onto the open internet is possible but not recommended without a reverse proxy (Caddy, nginx, etc.) in front of it terminating real TLS first — this is a plain-HTTP dev server underneath, and the login/CSRF protection built into the app is not a substitute for encrypting the connection itself. Leave CADRE_HOST at its default (127.0.0.1) for this option — only the proxy needs to be reachable from outside, not this app directly.

You'll need a domain name (or subdomain) pointed at your home's public IP — a dynamic DNS provider (e.g. DuckDNS, No-IP) if that IP isn't static — since automatic HTTPS needs a real hostname to issue a certificate for, not a bare IP address. Caddy is the least setup of the common options — it gets you real HTTPS with no manual certificate handling:

  1. Install it: caddyserver.com/docs/install has per-OS instructions.
  2. Create a Caddyfile next to wherever you run it from: 
    your-domain.example.com {
    reverse_proxy 127.0.0.1:7420
}
  3. Run it: caddy run (or install it as a service — see Caddy's own docs for that). It requests and renews the certificate automatically the first time it starts.
  4. On your router, forward ports 80 and 443 to this machine (Caddy needs port 80 briefly to complete the certificate challenge, then serves everything over 443) — not port 7420.

From there, https://your-domain.example.com reaches Cadre through Caddy, TLS included. This is genuinely more setup than Tailscale above (a domain, DNS, router configuration, a second process to keep running) — worth it only if you specifically need Cadre reachable by something that can't run Tailscale itself.

Keeping Cadre updated

Settings shows the version you're running and a "Check for updates" button. If a newer release exists, an "Update now" button appears — click it and it updates in place (git pull for a git-clone install, or downloads and applies the latest release ZIP otherwise), reinstalls dependencies, and restarts the dashboard automatically once it's back. The session daemon is never touched by this, so live sessions aren't affected. Works regardless of how you installed — git clone or the Windows ZIP-download path both work from this one button.

Installing on a new machine, running as a background service, uninstalling, or building the Windows installer — see SETUP.md and README.md on GitHub.
